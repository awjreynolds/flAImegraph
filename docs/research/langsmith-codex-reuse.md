# Codex tracing reuse: LangSmith and Langfuse source audit

Checked 6 September 2026. LangSmith and Langfuse already provide useful Codex turn/tool/subagent traces. They are substantial prior art for flAImegraph, but neither inspected parser handles the additive response records observed in Codex 0.153.4. Their existing trace output is therefore not a sufficient source of truth for this project's response accounting or context attribution.

The strongest reuse opportunities are LangSmith's coding-agent metadata contract and subagent discovery, and Langfuse's separate local parser and correctly nested usage categories. Keep a native, provenance-preserving accounting layer before either backend export.

## Scope and source pins

This was a static source audit. Public source was downloaded into temporary directories; no plugin was installed, built, tested, enabled, or run. No provider requests or trace uploads were made. Findings below distinguish directly observed code from predicted edge-case behavior. MIT licenses permit reuse subject to retaining their notices; no upstream source has been copied into the product.

The comparator is this project's [sanitized Codex capture validation](https://github.com/awjreynolds/flAImegraph/blob/main/docs/research/codex-capture-validation.md), based on an explicitly scoped local capture of Codex **0.153.4**. Its `token_usage_record` shape is observed evidence, not an official, stable public export contract. That capture has 177 distinct additive response records, 186 legacy `token_count` snapshots, and a compaction checkpoint containing previously observed usage. All six summed additive quantities reconcile with their corresponding final included per-thread counters.

## LangSmith: the CLI delegates ingestion

`langsmith trace setup codex` writes Codex configuration and adds `langchain-ai/langsmith-codex-plugins`; it does not contain the rollout parser. The plugin's Stop hook invokes its bundled `dist/index.mjs`. That entry point constructs a LangSmith `Client`, optionally reconstructs a distributed `RunTree` parent, and calls `convertToRunTree`. The checked-in bundle contains the same legacy usage handler and reasoning/cache mapping described below. [CLI setup](https://github.com/langchain-ai/langsmith-cli/blob/4520c970220b5029af76df70bfb37c079e0bb21d/internal/cmd/setup_codex.go#L19), [hook](https://github.com/langchain-ai/langsmith-codex-plugins/blob/62ee725be3d80776776f0ddaf7aa5a6874eead19/plugins/tracing/hooks/hooks.json), [entry point](https://github.com/langchain-ai/langsmith-codex-plugins/blob/62ee725be3d80776776f0ddaf7aa5a6874eead19/plugins/tracing/src/index.ts)

| Concern | Source finding | Consequence for reuse |
| --- | --- | --- |
| Additive response accounting | The parser handles `event_msg` with `payload.type === "token_count"`. It has no handler for `token_usage_record` and no `response_id` accounting key. | It discards the richer additive identity/scope surface in the inspected 0.153.4 capture. Legacy snapshots cannot be treated as an equivalent response ledger. |
| Legacy snapshot assignment | `last_token_usage` is attached to the most recent response item, while `total_token_usage` is stored on the task. There is no comparison of successive cumulative counters or response-level deduplication. | Adjacent repeated snapshots overwrite the same item harmlessly, but a repeated snapshot after a different item can reassign old usage. This is an ordering heuristic, not cumulative reconciliation. |
| LLM boundaries | Adjacent messages with the same AI role are merged; the last non-null usage wins. A LangSmith LLM child is created for each merged AI message. | Two distinct responses without an intervening different-role item can collapse, losing the earlier usage. One merged AI block is not demonstrably one provider response. |
| Tool-only model responses | Function/custom/tool-search calls become AI messages, so assistant prose is not required to produce an LLM run. Tool outputs are matched by call ID. | Useful coverage, but it depends on specific response-item formats and correct usage ordering. A token snapshot after a tool output is assigned to that tool output, not the model response. |
| Tool span edge case | Tool outputs following an AI message are selected only up to a following non-tool item. When there is no later non-tool item, the selection falls back to length 1. | Static walkthrough predicts trailing tool outputs are omitted as tool runs when the turn ends immediately after them. No synthetic execution was performed. |
| Cache and reasoning | `input_tokens`, `output_tokens`, and `total_tokens` pass through; cached input maps to `input_token_details.cache_read`. **`reasoning_output_tokens` maps to `input_token_details.cache_creation`.** | This is a concrete category error: reasoning output is not cache-created input. The observed newer `cache_write_input_tokens` category is unsupported. The mapping is present in source, bundled output, and test expectations. |
| Parent totals | Cumulative usage is emitted under the non-reserved `ls_raw_aggregated_usage` key; a comment explains that backend aggregation already sums child LLM usage. | This correctly avoids injecting a second reserved parent usage total, but the raw cumulative counter is not necessarily a turn delta and does not validate the child sum. |
| Subagent discovery | Supports legacy `spawn_agent` call/output IDs, `collab_agent_spawn_end`, `sub_agent_activity`, and completed `SubAgentActivity`/`CollabAgentToolCall` items. Searches the sessions tree for the child thread's rollout. | Valuable, concrete cross-version discovery logic; missing child files are silently skipped rather than represented as an explicit coverage gap. |
| Ancestry | Supports `source.subagent.thread_spawn` and newer `thread_source`/`parent_thread_id`. Recursively uploads child rollouts under the current parent turn. Child metadata groups its conversation under its immediate parent thread. | A real nested trace is constructed, but the code does not consume additive `root_turn_id` or resolve a transitive root-thread identity. A depth-two child's metadata can group under the intermediate agent. |
| Follow-up turns | Discovery is associated with the spawning turn; recursive conversion processes available child turns, with a per-rollout upload ledger. | It does not establish ownership of every later child turn under the actual initiating root turn. Already-uploaded child turns are skipped; which hook reaches a child first matters to tree construction. |
| Compaction | Types mention compaction, but the conversion loop has no `compacted`/`context_compacted` handling. The metadata type permits `compaction` without emitting such a run here. | No compaction boundary, replacement-history transformation, compaction-response accounting, or checkpoint replay rule is implemented. |
| Request inputs and timing | Each task resets at `task_started`; LLM inputs are base instructions plus the reconstructed prefix available inside that task. LLM start time is inferred from the preceding message's end. | These are transcript-derived representations and timing estimates. They are not captured final provider requests, complete retained context, exact model latency, or per-source token composition. |

### Replay and delivery are different questions

The `.langsmith` sidecar stores uploaded turn IDs, preventing a normal subsequent hook from replaying the whole completed conversation. It is not a ledger of immutable response usage records, payload fingerprints, cumulative corrections, or delivery acknowledgements. The parser also treats a trailing event as a flush when the hook supplies a turn ID, then marks that ID. An incomplete turn can consequently become ineligible for later reconstruction. [Sidecar](https://github.com/langchain-ai/langsmith-codex-plugins/blob/62ee725be3d80776776f0ddaf7aa5a6874eead19/plugins/tracing/src/sidecar.ts), [flush and mark ordering](https://github.com/langchain-ai/langsmith-codex-plugins/blob/62ee725be3d80776776f0ddaf7aa5a6874eead19/plugins/tracing/src/trace.ts#L891)

`postRun()` promises enter a queue; sidecar marking occurs before the final `Promise.all` over that queue. Static control-flow analysis therefore does not establish transactional or exactly-once delivery. A robust local accounting design needs independent parse-state, correction, and export-delivery state, with acknowledgement semantics verified against the chosen SDK/backend.

### Local export and dependency boundary

The Go CLI's `trace export` and `run export` query a LangSmith backend and then write JSONL. They are useful export paths for already-ingested data, not commands that convert a local Codex rollout offline. `trace export` fetches a bounded set of traces and requests up to 1,000 runs for each selected trace, so completeness also needs explicit handling for large trees. [Trace export](https://github.com/langchain-ai/langsmith-cli/blob/4520c970220b5029af76df70bfb37c079e0bb21d/internal/cmd/trace.go#L255), [run export](https://github.com/langchain-ai/langsmith-cli/blob/4520c970220b5029af76df70bfb37c079e0bb21d/internal/cmd/run.go#L177)

The TypeScript converter accepts a supplied `Client`; its tests capture requests with a mock fetch implementation. An offline sink could therefore be engineered, but this is not a supported pure-data parser/export command. The current converter is coupled to LangSmith `RunTree` construction, posting, sidecars, filesystem reads, and git metadata lookup. Its package declares `langsmith` `^0.8.11`; the normal entry point uploads transcript content. [Dependencies](https://github.com/langchain-ai/langsmith-codex-plugins/blob/62ee725be3d80776776f0ddaf7aa5a6874eead19/package.json), [mock client](https://github.com/langchain-ai/langsmith-codex-plugins/blob/62ee725be3d80776776f0ddaf7aa5a6874eead19/plugins/tracing/test/utils/mock_client.ts)

The reusable metadata layer is particularly valuable: `coding-agent-v1` carries runtime/integration/schema identity, turn/thread grouping, versions, repository and workspace metadata, with scope-specific subagent fields. It provides interoperability vocabulary, not an accounting or context-provenance guarantee. [Metadata implementation](https://github.com/langchain-ai/langsmith-codex-plugins/blob/62ee725be3d80776776f0ddaf7aa5a6874eead19/plugins/tracing/src/metadata.ts), [contract tests](https://github.com/langchain-ai/langsmith-codex-plugins/blob/62ee725be3d80776776f0ddaf7aa5a6874eead19/plugins/tracing/test/contract.test.ts)

## Langfuse: a cleaner parser seam, with the same additive gap

Langfuse exposes `parseSession(lines)` separately from its emitter. It returns session metadata and turns containing model steps and tool calls; the parser imports local types/utilities rather than a backend client. This is a more direct model for a reusable local adapter. Its `ModelStep` is still reconstructed around legacy `token_count` events. The parser closes an existing step on each such event; consecutive duplicate snapshots with no new step do not create another step. It does not reconcile cumulative differences or key usage by response ID. Usage without any recognized model step is not retained as an independent response record. [Parser](https://github.com/langfuse/codex-observability-plugin/blob/1db5c0f5ddce569afc112c6476e21d00cf9a482e/plugins/tracing/src/parse.ts#L99)

Its usage conversion preserves inclusive input and output totals and encodes cached tokens beneath prompt details and reasoning beneath completion details. It validates nonnegative safe integers, input + output = total, cached <= input, and reasoning <= output; invalid usage is dropped with a debug message. This is substantially closer to the required accounting semantics, though a provenance-oriented local tool should retain rejected raw records and explain the coverage gap instead of relying on debug output. [Usage conversion](https://github.com/langfuse/codex-observability-plugin/blob/1db5c0f5ddce569afc112c6476e21d00cf9a482e/plugins/tracing/src/trace.ts#L113)

Function/custom/local-shell/web-search calls can create model steps without assistant prose. Tool calls are matched by ID, enriched from end events, and emitted as children of their generation. Subagents discovered from spawn/activity events are nested under the spawning turn. This brief comparison found no `token_usage_record`/`response_id` support; `compacted` is explicitly documented in its local types as ignored. Session parsing detects newer parent/thread-source fields but does not retain full ancestral/root-turn ownership. [Tool and lifecycle parsing](https://github.com/langfuse/codex-observability-plugin/blob/1db5c0f5ddce569afc112c6476e21d00cf9a482e/plugins/tracing/src/parse.ts#L199), [types](https://github.com/langfuse/codex-observability-plugin/blob/1db5c0f5ddce569afc112c6476e21d00cf9a482e/plugins/tracing/src/types.ts)

The emitter sends only the user prompt for the first generation and previous tool results for later generations, rather than a full serialized model request. All available turns in a discovered subagent rollout are nested under the current spawning turn, without subagent deduplication. Top-level completed turns use a `.langfuse` sidecar; incomplete turns are intentionally re-emitted. These are useful tracing policies but do not implement response-level replay/correction or precise follow-up ownership. [Emission and deduplication](https://github.com/langfuse/codex-observability-plugin/blob/1db5c0f5ddce569afc112c6476e21d00cf9a482e/plugins/tracing/src/trace.ts#L203)

The production hook requires Langfuse credentials and configures `LangfuseSpanProcessor` on an OpenTelemetry provider. It batches spans and flushes during shutdown, after conversion and sidecar marking. The local pure parser can be reused or adapted independently, but no supported standalone local-file export command was found in this bounded inspection. Replacing the production exporter with a local OTel sink would be an implementation change. [Instrumentation](https://github.com/langfuse/codex-observability-plugin/blob/1db5c0f5ddce569afc112c6476e21d00cf9a482e/plugins/tracing/src/instrumentation.ts), [hook entry](https://github.com/langfuse/codex-observability-plugin/blob/1db5c0f5ddce569afc112c6476e21d00cf9a482e/plugins/tracing/src/index.ts)

## Implications for flAImegraph

1. Preserve native additive records first: observed thread/session/turn/root-turn/response identities, all six token quantities, source line/hash, runtime version, and capture bounds. Deduplicate by identity with explicit conflict/correction handling; retain cumulative counters as reconciliation evidence.
2. Implement legacy `token_count` support as a separate adapter with fixtures for duplicate snapshots, usage after tool outputs, adjacent assistant responses, missing response items, interrupted turns, and partial files. Do not silently substitute message grouping for response identity.
3. Treat cached input and reasoning output as subsets; keep cache-write input separate when observed. Never add subsets to their containing totals or map reasoning to cache creation.
4. Reuse metadata names and discovery ideas while retaining both direct parent and true root ownership. A nested display tree must not overwrite the initiating `root_turn_id` of a later delegated turn.
5. Represent compaction boundaries, replacement history and opaque state explicitly. A checkpoint carrying old usage is replayed evidence, not new consumption. Neither audited integration supplies exact request-source attribution.
6. Export the normalized data to existing backends if useful. Keep local accounting and coverage checks independent of backend tree aggregation, uploaded-turn sidecars, query limits, and exporter success.

This audit narrows the opportunity: existing products already cover broad trace visualization and multi-agent instrumentation. The defensible additional work is trustworthy local accounting across evolving harness formats, transparent missingness and corrections, preserved work ownership, and honest separation between request totals, context representation and causal usefulness.
