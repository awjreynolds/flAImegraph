# Existing AI telemetry coverage and tokenomics accounting gaps

Research date: 2026-09-06. Decision ticket: **What AI usage and execution semantics already exist?**

## Verdict

OpenTelemetry GenAI already supplies most of the vocabulary and transport foundations needed for token-weighted visualisation. OpenInference offers another established vocabulary over the same trace infrastructure. Neither inspected surface constitutes a complete ticket-to-epic accounting contract. The strongest opportunity is to demonstrate consistent attribution and totals from imperfect, overlapping observations, then contribute specific semantics upstream. A new universal vocabulary or transport is not justified by this investigation.

That opportunity is not unclaimed territory. Existing OpenTelemetry discussions address precisely the dangerous boundaries: [Aggregated token usage attributes](https://github.com/open-telemetry/semantic-conventions-genai/issues/19), [Operations versus attempts](https://github.com/open-telemetry/semantic-conventions-genai/issues/476), and [Per-operation cost conventions](https://github.com/open-telemetry/semantic-conventions-genai/pull/443). The retry discussion also identifies [AgentMeasure](https://github.com/roy-tong/AgentMeasure) as adjacent prior art; its complete semantics require a separate comparison.

## What the measurements actually mean

The most consequential correction to the earlier conversation is that OTel usage is not universally physical model consumption. Its registry prefers the billed count if a provider supplies both billed and consumed counts, citing Cohere. Cached input is included in input totals. Reasoning output is included in output totals. Cached text is simultaneously a subset of cached input and text input. Consequently, categories form overlapping sets rather than a flat additive list. [Pinned registry](https://github.com/open-telemetry/semantic-conventions-genai/blob/94f432d7126f5884d30a2cdde6f4e89908ebb6fd/model/gen-ai/registry.yaml#L267).

For example, consider 1,000 input tokens including 600 cached tokens. A width of 1,600 derived by adding input and cache-read is incorrect. Similarly, 400 output tokens including 250 reasoning tokens remain 400 output tokens. A provider that reports 1,000 consumed but 900 billable tokens introduces a different distinction: the standardized OTel total can be 900. Retaining the provider's original measurement names and count basis would preserve a physical-consumption view as well as the standardized billing-oriented view. These are illustrative accounting consequences, not additional upstream requirements.

Provider normalization is already specified: OTel's Anthropic mapping adds cache-read and cache-write input to the provider's otherwise noncached input. A generic adapter that blindly copies a field called `input_tokens` would therefore be wrong for that mapping. [Provider span definition](https://github.com/open-telemetry/semantic-conventions-genai/blob/94f432d7126f5884d30a2cdde6f4e89908ebb6fd/model/gen-ai/spans.yaml#L835).

OpenInference's actual OpenAI completion extractor copies reported totals, prompt/completion counts and available cached/audio/reasoning detail, checking against `None` so valid zero values survive. This demonstrates an observable distinction between zero and missing usage in an implementation. It does not establish that every provider adapter or failed request has equivalent coverage. [Extractor](https://github.com/Arize-ai/openinference/blob/87b54b85a97eb52ed4d506bc88e991acc26065d3/python/instrumentation/openinference-instrumentation-openai/src/openinference/instrumentation/openai/_response_attributes_extractor.py#L228).

## Hardest counterexamples

**An agent total overlaps its calls.** Suppose a parent reports 12,000 input tokens while two child calls report 7,000 and 5,000. Counting all three yields 24,000. Upstream's open aggregation discussion describes this exact class of problem. Agent usage groups exist, but the inspected common definitions do not supply a universal self/inclusive marker or a complete algorithm for reconciling partial descendants. [Aggregation discussion](https://github.com/open-telemetry/semantic-conventions-genai/issues/19). Merely discarding nonleaf spans also fails if an opaque hosted agent exposes only a total, or some children are missing. A proposed profiling contract should identify authoritative observations and retain unexplained residuals instead of assuming completeness.

**One logical call contains two chargeable attempts.** An automatic retry can occur inside one caller-level span. Separate HTTP spans may reveal requests without revealing token usage. If a failed first attempt has no returned usage, observing the successful second response cannot prove the total consumed. The open operations/attempts discussion asks how these units should relate to usage and success rate. [Retry discussion](https://github.com/open-telemetry/semantic-conventions-genai/issues/476). Recommended distinction: logical operation, observed attempt, and usage observation must be distinguishable even when instrumentation cannot populate all three.

**Usage arrives during later polling.** Current fetch-response conventions avoid counting previously generated tokens again. The open background-execution issue shows the opposite failure: initial submission returns before inference completes, so suppressing usage on the terminal poll can omit all consumption. Repeated polls can then observe the same usage multiple times. [Background usage discussion](https://github.com/open-telemetry/semantic-conventions-genai/issues/403). This supports stable observation identity and delayed reconciliation; it does not authorize treating every response fetch as new inference.

**A shared research run benefits two tickets.** A causal link can record a relationship to both contexts, but duplicating the full weight under both tickets doubles the epic total. The allocation question is a business policy: exclusive owner, proportional shares, or separate beneficiary and charged-owner views. Those choices should be explicit and reviewable. Nothing in a causal parent alone decides them. [Trace link semantics](https://opentelemetry.io/docs/specs/otel/trace/api/#link).

**The trace looks complete but is not.** Unsampled spans can disappear, a full batching queue drops spans, and export retries can duplicate delivered data. OTLP acknowledges delivery between neighboring nodes, not end-to-end accounting completeness. [SDK behavior](https://opentelemetry.io/docs/specs/otel/trace/sdk/), [OTLP](https://opentelemetry.io/docs/specs/otlp/). A candidate profile should state its capture boundary and whether totals are observed, reconciled or incomplete. Exact billing claims require stronger evidence than an apparently connected tree.

## Cost proposals and an upstream route

The open **Per-operation cost conventions** PR proposes `gen_ai.usage.cost.amount`, ISO currency, and a `provider|local` source distinction. Its revised scope places cost on inference spans to avoid overlap with agent/workflow totals; it excludes allocation, post-hoc enrichment, per-class breakdowns and pricing-source references for later work. Crucially, `provider` means received in the response and can include an intermediary: it is not proof of a finalized invoice charge. This remains a proposal under review. [Cost proposal](https://github.com/open-telemetry/semantic-conventions-genai/pull/443).

Existing agent metrics already express a useful conservation rule: an agent's inference-call count includes its own failed calls but excludes calls issued by subagents, which belong to their invocations. That rule is specific to that metric; it should not be generalized into an already-standardized token-aggregation contract. Detailed cache/reasoning metric dimensions also have their own open issue. [Metrics](https://github.com/open-telemetry/semantic-conventions-genai/blob/94f432d7126f5884d30a2cdde6f4e89908ebb6fd/docs/gen-ai/gen-ai-metrics.md#metric-gen_aiinvoke_agentinference_calls), [Detailed metrics discussion](https://github.com/open-telemetry/semantic-conventions-genai/issues/76).

The contribution route is concrete: focused changes to YAML definitions, generated documentation, policy checks, and reference scenarios demonstrating capturability. The GenAI SIG and its discussion channel are the documented venues. No outreach was performed. [Contributor guide](https://github.com/open-telemetry/semantic-conventions-genai/blob/94f432d7126f5884d30a2cdde6f4e89908ebb6fd/CONTRIBUTING.md).

## Next evidence needed

The reference suite already exercises SDKs against deterministic mock servers and validates captured output with Weaver. It is a useful foundation, not proof that installed product telemetry emits every standardized field. At the inspected revision, the inference report has much narrower conversation-ID coverage than general input/output-token coverage. [Reference methodology](https://github.com/open-telemetry/semantic-conventions-genai/blob/94f432d7126f5884d30a2cdde6f4e89908ebb6fd/reference/README.md), [Pinned coverage report](https://github.com/open-telemetry/semantic-conventions-genai/blob/94f432d7126f5884d30a2cdde6f4e89908ebb6fd/reference/reports/inference-span.md).

Before choosing a format extension, test actual exports from two target coding-agent systems against the counterexamples above. Establish whether usage is per call or cumulative, whether provider response IDs survive, which paths expose retries, and what a missing final streaming usage message looks like. Compare AgentMeasure's existing rules before designing new conformance language. Then separate proposals for generic accounting semantics from application-specific ticket ownership, and demonstrate that different adapters produce conserved totals—or explicitly report why the evidence cannot establish them.
